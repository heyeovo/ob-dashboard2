# CC 按天滚动上下文交接

## 当前完成状态

- 第一阶段已实现：同一逻辑聊天可在“原换窗机制 / 按天滚动”之间切换。
- 滚动模式由用户手动把每个聊天日设为 `原文 / 日回顾 / 不带`；默认日界线为北京时间 04:00，可在页面改整点。
- 每条 user/assistant 消息由 Haven 保存永久 `msg_*` ID 与 `chat_day`，旧数据启动时确定性回填。
- 聊天 UI 保持一条连续时间线，显示日期分隔，并可从顶部“历史”选择日期后在当前页面跳转。
- 钉选桶不再依赖冻结 handoff：滚动模式每轮读取 Haven 最新钉选正文。
- 召回排除按当前可见的原文日期计算；已转成日回顾或不带的日期，其旧召回桶可再次召回。
- 上下文配置仍保存 `context_revision + context_turn_watermark` 作为版本事实；原文日期从 Haven 永久消息恢复为真正的 `user/assistant` 对话流，不再包进 `rolling_window_context`。滚动 CC 进程内沿用当前原生会话，冷启动则按当前三态从 Haven 重建可见原文，不续接可能含旧包装内容的原生会话。
- CC 前台、后台 wake、Context GC 与 selfhost 均已适配。固定模式保留旧 handoff 行为，作为即时回退路径。
- 第一阶段已完成部署与真实验收；滚动上下文已支持手动加入钉选桶和未锁定日记。
- 后续补充已完成部署并通过手机点击验收：手机端 `/cc` 默认进入对话列表，每个协作者可手动指定唯一主窗；历史聊天/已删除窗口分为子列表。
- 从滚动切回固定模式仍不会自动重做 handoff；设置页已增加常驻警告和保存确认。要保留滚动期间的新对话，仍需使用“换窗继续”。

## 已确认的产品决定

- “主滚动窗”不是全局唯一的滚动对象，而是某个用户主动开启按天滚动的普通 session。新增的“主窗”只是每个协作者手动选择的唯一列表置顶标记，不会自动开启滚动；滚动配置、聊天历史、context revision 和 Claude 原生 session 均按 `session_id` 隔离。
- 不取消创建其他独立窗口做测试、跑代码等能力；其他新窗口默认继续使用原换窗机制。不同窗口仍共享协作者提示词与长期记忆库，只有聊天上下文和运行会话相互独立。
- 第一阶段全手动，不做每轮自动压缩，也不自动生成日回顾。
- 用户每天只需在合适时机手动保存一次日期三态；保存时生成 revision + turn watermark。CC 新 revision 首轮把所选原文按角色恢复进 transcript，之后进程内由原生会话自然承接；selfhost 每轮按同一三态重建 messages。
- 上下文版本保存引用与配置，不保存每次请求的整份上下文副本。
- 手动桶与未来自动切片是两条召回线：手动桶数量少、重要性高；自动切片更精简、碎片化，用于补足没被手动存下的生活细节。
- 自动切片不进入现有桶表，不改变手动存桶、评分或合并逻辑。
- 旧消息编辑/重新生成不在本阶段。

## 总体实施路线

### 阶段一：手动按天滚动（已部署验收）

- 永久消息 ID、聊天日期、逐日三态、版本水位线、热更新钉选、可见日期召回排除、连续历史 UI 和两种执行器适配已经完成。
- 滚动模式核心已经在真实主窗验收；后续继续观察长期体验。
- 对话列表、主窗置顶、删除修正与切换警告已按 Haven → Dashboard 顺序部署并完成手机点击验收。旧窗口和新窗口默认都不会自动开启滚动。

### 阶段一点五：真实体验与稳定

先实际使用一段时间，不预设滚动一定优于换窗。重点观察：

- 情感语气是否比手动换窗更稳定、衔接是否更自然。
- 保存新 revision 后的首轮 Context、缓存写入量和回复延迟是否可接受。
- 最近原文是否过多或过少；默认“最近 3 个有聊天的日期原文 + 更早最多 10 个日回顾”是否需要调整。
- 日期从原文退出后，旧桶能否自然恢复召回，是否出现明显重复或遗忘。
- 钉选桶修改后是否下一轮生效。
- 主滚动窗和临时独立窗口来回切换时是否串 context。
- 同一窗口切回固定模式的体验是否清楚；如要保留滚动期间的最新衔接，应从当前窗口重新执行一次“换窗继续”，而不是依赖最初的旧 handoff。

体验期发现的问题优先做小修正，不同时启动自动切片，避免难以判断问题来自哪一层。

### 阶段二：自动聊天切片摘要

> 详细数据契约、离线生成、人工检查、影子召回和正式 Context 接入门禁，统一维护在 `HANDOFF-cc-auto-chat-slices.md`；本文件不再复制后续阶段计划。

- 自动聊天切片摘要：按自然话题/事件边界生成更精简、碎片化、第一人称的生活细节摘要，走独立于手动桶的召回线。
- 切片数据至少需要：独立 slice ID、session ID、起止永久 message ID/source range、聊天日期、摘要正文、时间范围、生成版本、内容 hash、创建/更新时间和失效状态。
- 同一 source range + 生成版本必须幂等，重复任务不得生成重复切片；原文改变或重切片时要能让旧切片失效，而不是静默覆盖后失去追溯。
- 召回前先按当前滚动配置过滤：source range 所属日期仍为原文可见时不召回；日期进入日回顾或不带后恢复召回资格。
- 切片召回与手动桶分别检索、分别限额，最终再做跨线去重；手动桶优先保留，切片负责补充小细节，不能用大量相近切片淹没重要记忆。
- 切片正文以第一人称记录事件、情绪、感受和关键指代，但比日回顾更局部、比原文更省 token；必要时可凭 source message ID 回查原文全貌。
- 实施顺序必须是：数据契约与幂等/重切片设计 → 离线生成与人工检查 → 独立召回观察 → 最后才接入正式模型 Context。

### 低优先级后续

- 评估“凌晨 3 点后且沉默超过 1 小时才结束当天”的动态日界线；当前仅支持可配置整点，默认北京时间 04:00。
- 旧消息编辑、重新生成及其引发的下游消息/切片失效链。
- 如有需要，再设计完全不共享长期记忆的隔离测试窗；当前临时窗口只隔离聊天 Context，不隔离同一协作者的记忆库。

## 回退策略

- **未启用即无影响**：默认始终是原换窗机制，部署不会自动转换任何窗口。
- **单窗口停止滚动**：在“本窗 → 上下文拼接”切回“原换窗机制”。如果需要带上滚动期间的最新内容，推荐从当前窗口重新“换窗继续”创建固定窗口。
- **整体代码回退**：对 Dashboard 和 Haven 本功能提交分别执行 Git revert 后重新部署。数据库迁移只新增字段/表，不删除旧对话；旧代码会忽略新增结构。
- 为方便整体回退，本功能应尽量形成可识别的独立提交；不需要为此改变用户长期直接提交 `main` 的习惯。

## 不得扩散的边界

- 不改长期桶本身的含义、评分或手动存桶流程。
- 不删除旧 handoff、Context GC、自建引擎或独立窗口能力。
- 不把切片摘要混进现有桶表。
- 不把所有对话强制合并进一个长期窗口，也不取消独立新窗口。

## 验收方法

1. 打开 `/cc` → 顶部“本窗” → “上下文拼接”，启用按天滚动。
2. 把最近日期分别设成原文、日回顾、不带并保存；下一句话应使用新 revision，旧 Claude session 不得被恢复。
3. 修改一个钉选桶正文，下一轮应看到新正文。
4. 将某个原文日改为日回顾后，该日曾召回的非钉选桶应恢复召回资格。
5. 点击顶部“历史”，选日期后应在同一聊天时间线跳到当天，并可继续上下滚动。
6. 切回“原换窗机制”，旧窗口 handoff 行为应恢复。
7. 手机进入 `/cc` 应先看到对话列表；置顶一个窗口后只允许一个主窗，点入聊天后左上角和底部聊天 Tab 均可返回列表。
8. 删除普通窗口后，它应立即从最近对话移入“已删除窗口”，且后台 wake 不能让它重新出现。
9. 已删除窗口超过 60 个时，入口计数应显示真实总数，子列表底部应出现“加载更多”。
10. 在模型请求记录中检查滚动“原文”日期：应表现为交替的 `user/assistant` messages；`rolling_window_context` 只能包含日回顾、钉选桶和日记，不能再出现完整对话原文。
